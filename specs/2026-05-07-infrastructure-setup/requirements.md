# Requirements: 项目基础设施搭建

## 范围

### 包含（In Scope）

- 项目依赖管理和环境配置（`pyproject.toml`、`uv.lock`）
- 公共工具库（`src/`）的接口定义和基础实现
- 全局配置模板（`configs/base_config.yaml`）
- MLflow 实验追踪的基础封装（本地文件系统存储）
- 项目目录结构的标准化模板
- 代码质量工具配置（ruff）
- 基础验证脚本和集成测试

### 不包含（Out of Scope）

- 具体案例的业务逻辑（属于 Phase 1-7）
- MLflow UI 服务器的部署和配置（仅封装 tracking API）
- Docker 环境封装
- CI/CD 流水线
- 完整的单元测试覆盖（仅做基础导入和运行验证）

## 关键决策

### 决策 1：使用 uv 作为包管理器

- **背景**：项目需要快速、可靠的依赖管理，且要求环境可复现
- **选择**：uv（Rust 实现，原生 lock 文件，比 pip/conda 快 10-100x）
- **影响**：所有开发者必须安装 uv，不再使用 pip 或 conda

### 决策 2：MLflow 使用本地文件系统存储

- **背景**：需要实验追踪，但不需要生产级部署
- **选择**：tracking URI 设为 `./mlruns/`，不启动 MLflow server
- **影响**：实验记录存储在项目目录下，不提交到 Git，仅本地可用

### 决策 3：公共库采用"最小可用"原则

- **背景**：公共库过早过度设计会增加维护成本
- **选择**：先定义核心接口和常见场景的实现，具体案例使用时按需扩展
- **影响**：`src/` 中的函数可能初期只覆盖 80% 的场景，剩余 20% 在各案例中自行补充

### 决策 4：配置采用 YAML 文件驱动

- **背景**：每个案例需要独立配置，且希望参数与代码分离
- **选择**：每个案例一个 `config.yaml`，继承 `configs/base_config.yaml` 的默认值
- **影响**：修改参数不需要改代码，便于实验复现和超参搜索

## 背景信息

### 为什么 Phase 0 必须先完成

根据路线图规划，7 个案例共享同一套基础设施。如果跳过此阶段直接开始案例开发：

- 每个案例都需要重复编写数据加载代码，违背 DRY 原则
- 不同案例的 MLflow 实验记录格式不一致，难以横向对比
- 代码风格和目录结构混乱，后期重构成本高

### 成功标准（来自 mission.md）

完成 Phase 0 后，应能在 5 分钟内从零开始创建一个新的案例目录并运行代码。

### 技术约束（来自 tech-stack.md）

- Python 3.11+
- 核心库：pandas, numpy, scikit-learn, LightGBM, XGBoost, SHAP, MLflow, Optuna
- 代码风格：ruff 格式化，最大行宽 100
- 所有文档和注释使用中文
